# Dimensional modeling cheatsheet

Reference for the Learning path "Warehouse and dbt". The BI Lab runs warehouse SQL for real on the local DuckDB
catalog; its star model checks are real queries, and column lineage is a static analysis of the SQL text.

## Facts and dimensions

| | Fact table | Dimension table |
|---|---|---|
| Holds | events or measurements | descriptive context |
| Row | one per declared grain (one sale line, one day per product) | one per member (or per version) |
| Columns | foreign keys + numeric measures | surrogate key, business key, attributes |
| Size | long and narrow | short and wide |

Star schema: facts in the center, one join to each denormalized dimension. Flatten snowflaked hierarchies
(product → category → department) into the dimension.

## Declare the grain first

1. Choose the business process (orders, shipments, stock).
2. Declare the grain: "one row per order line".
3. Attach the dimensions that are true at that grain.
4. Add the measures that are true at that grain.

Order-level amounts (shipping fee) must be allocated to the lines so that they sum back exactly, or kept in an
order-grain fact.

## Measures

| Kind | Sum across | Example |
|---|---|---|
| Additive | every dimension | sales amount, quantity |
| Semi-additive | not across time | stock on hand, account balance |
| Non-additive | never | unit price, margin %, ratios (recompute from additive parts) |

## Fact table types

- **Transaction**: one row per event.
- **Periodic snapshot**: one row per entity per period (stock per product at month end).
- **Accumulating snapshot**: one row per process instance, updated at each milestone (order placed, shipped, delivered).
- **Factless**: keys only, for coverage or events without measures (products on promotion).

## Keys

- **Surrogate key**: generated by the warehouse, stable, one per SCD2 version.
- **Business (natural) key**: from the source system.
- **Unknown member**: a fixed row (key -1 or 0) that facts point to when the dimension value is missing.
- **Inferred member**: a placeholder created for a fact that arrives before its dimension row, completed later.

## Slowly changing dimensions

| Type | On a change | History |
|---|---|---|
| 1 | overwrite the attribute | none |
| 2 | close the current row, insert a new version | full |
| 3 | keep the previous value in a second column | one step |

Type 2 columns: `customer_key` (surrogate), `customer_id`, attributes, `valid_from`, `valid_to` (exclusive,
`9999-12-31` while current), `is_current`.

```sql
-- Versions from a change log; keep only real changes.
SELECT customer_id, city, changed_at AS valid_from,
       COALESCE(LEAD(changed_at) OVER w, DATE '9999-12-31') AS valid_to
FROM (
  SELECT *, LAG(city) OVER (PARTITION BY customer_id ORDER BY changed_at) AS previous_city,
         ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY changed_at) AS n
  FROM changes
) AS c
WHERE n = 1 OR city IS DISTINCT FROM previous_city
WINDOW w AS (PARTITION BY customer_id ORDER BY changed_at);

-- Point-in-time join: the version valid when the sale happened.
SELECT s.sale_id, d.city
FROM sales s
JOIN dim_customer d
  ON d.customer_id = s.customer_id
 AND s.sold_on >= d.valid_from AND s.sold_on < d.valid_to;
```

Compare tracked attributes with `IS DISTINCT FROM`: `<>` misses changes to or from NULL.

## Many-to-many

A bridge table between a fact and a multi-valued dimension (an account with several holders), with allocation weights
that sum to 1 per group so totals do not double count. Drill across two facts by aggregating each to the shared
dimensions first, then joining the results.
